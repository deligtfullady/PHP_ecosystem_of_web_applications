**Результат взаимодействия с systemctl** (ожидаемое поведение; сверьте со своим выводом после запуска)

```bash
sudo cp deploy/systemd/worker.service /etc/systemd/system/reminder-worker.service
sudo systemctl daemon-reload
sudo systemctl enable --now reminder-worker
systemctl status reminder-worker      # Active: active (running), Main PID, последние строки лога
sudo systemctl reload reminder-worker # SIGHUP → демон сохраняет позицию и выходит → Restart=always поднимает заново
sudo systemctl stop reminder-worker   # SIGTERM → «worker остановлен, позиция сохранена», Active: inactive (dead)
sudo kill -9 <MAIN PID>               # SIGKILL → systemd перезапустит через RestartSec=3, минута in_progress повторится
journalctl -u reminder-worker -f      # логи
```

**Когда демон лучше crontab**

| Демон (supervisor / systemd) | crontab |
|---|---|
| Интервал меньше минуты или реакция «сразу» (очередь, long polling) | Простые периодические задачи раз в минуту и реже (бэкап, отчёт) |
| Долгоживущие соединения: RabbitMQ, Redis, Telegram | Задача независима и не хранит состояние |
| Дорогой старт (подключения, прогрев) делается один раз | Нужна «самоочистка»: процесс завершился — память освободилась |
| Нужны мягкая остановка по сигналу и автоперезапуск | Достаточно «запустить по расписанию, не заботиться о перезапусках» |
| Состояние в памяти (offset, история диалогов) | Лёгкая настройка без прав root (`crontab -e`) |

В проекте: `tg_messages` и `queue_manager` — демоны (долгий опрос и потребитель очереди); `handle_events` можно запускать
и cron'ом (`* * * * *`), и демоном `worker` — второй вариант не теряет минуты при перезапуске.

**Какой тип аутентификации использовали?** — **API-ключ (token-based, «API key»)**: BotFather выдаёт статический секретный токен,
который передаётся прямо в URL: `https://api.telegram.org/bot{token}/getUpdates`. Это именно *аутентификация* (токен
доказывает, что запрос от нашего бота); *авторизация* отдельно не настраивается — токен даёт полный доступ к боту.
Это не Basic, не Bearer-заголовок, не OAuth и не JWT. Минус — токен попадает в URL (логи прокси, трассировки), поэтому он лежит в
`.env` (не в Git), в исключениях приложения не печатается (`TelegramApiImplTest`), а при утечке перевыпускается у BotFather (`/revoke`).

**Диалог (⚹3).** `/start` → «Укажите название события» → «Укажите ID пользователя» → «Укажите текст напоминания» →
«Укажите cron-расписание» → «Я записал Ваше событие. Для нового события введите /start». Сообщения/offset хранятся в кэше;
ID и cron проверяются на каждом шаге — при ошибке бот переспрашивает тот же вопрос.
Чужой получатель: он должен сначала написать боту (иначе Telegram вернёт «chat not found»).

(`sendMessage` → `toQueue`), `QueueManagerCommand` (`php runner -c queue_manager`) отправляет их в Telegram.

Отличия от слайдов (осознанные): в интерфейс `Queue` добавлен `rejectLastMessage()` — при ошибке Telegram сообщение
возвращается в очередь (nack + requeue), а не «зависает» неподтверждённым; повреждённое сообщение подтверждается и отбрасывается
с исключением, чтобы не зациклить обработчик.

## Улучшения сверх заданий

- Полноценный разбор cron (списки, диапазоны, шаги, 0/7 для воскресенья, правило «день месяца ИЛИ день недели»), валидация при сохранении.
- Демон: догон пропущенных минут, повтор незавершённой минуты, атомарная запись состояния, защита от второго экземпляра, выход после 10 ошибок подряд (перезапустит supervisor/systemd).
- Надёжная отправка: очередь + requeue при ошибке Telegram; токен не попадает в тексты исключений.
- Ошибки пользователя в диалоге не ломают его — бот переспрашивает тот же вопрос.

## Известные ограничения

- Гарантия «минимум один раз»: при сбое после отправки в очередь, но до сохранения offset, возможны повторы ответов.
- В cron не поддерживаются названия (MON, JAN) и макросы (@daily).
- Код написан без возможности запустить PHP в среде разработки: перед сдачей выполните `composer install` и `phpunit`.
